# CI quality gates

PR CI MUST include lint/format, automated tests, build verification, dependency
and secret checks, and migration/API contract checks where applicable. Integration
tests SHOULD use isolated disposable databases and deterministic fixtures.
Explicit opt-in and exact target validation MUST precede destructive test setup.
CI failure blocks merge except an approved emergency procedure.

## Gate design

Each adapter MUST enumerate required checks, commands, triggers, supported
runtimes and test groups: unit, integration, contract, ops, browser and device
checks as applicable. Run meaningful negative authorization, concurrency and
failure-path tests for critical behavior. Coverage percentages alone do not
establish safety.

Use a required aggregate gate that runs for every PR. Expensive jobs may be
selected by changed paths, but the aggregate MUST fail for failed, cancelled or
unexpectedly skipped required jobs. Document legitimate not-applicable jobs.
Do not require a path-filtered workflow that can remain pending forever.

Use the same command implementations locally and in CI. Require applicable
lint/format/static checks, application-source type validation
for supported stacks, build verification, dependency audit and repository-wide
secret scanning where applicable. Targeted regex checks do not replace a secret
scanner. An exception needs an owner, expiry and compensating control.

Declare unsupported checks with reviewed rationale and compensating validation;
never label an unconfigured command as PASS. Routine CI-skip markers are not an
alternative to required checks on the reviewed revision. Product release checks
include applicable integration, migration and contract validation even when not
all run for a documentation-only PR.

## Workflow safety and evidence

Use least-privilege permissions, trusted actions pinned to audited full commit
SHAs, minimal secrets and scoped caches. Never expose production credentials to
untrusted PR code. Separate validation from deployment.

Record check URLs, reviewed full source SHA and tool/config versions. Exercise
both a passing and deliberately failing PR before marking the gate operational.
A workflow file with no accessible execution evidence is NOT_ASSESSED, not PASS.

The [CI sample](../templates/github/workflows/ci-example.yml) deliberately fails
until configured. This handbook's own link-validation workflow is not a product
quality gate.
